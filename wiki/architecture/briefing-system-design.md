# 일일 브리핑 시스템

사용자 요청(2026-09-11) — "한국 아침에 밤사이 미국을 정리해 오늘 한국을
전망하고, 한국 저녁에 오늘을 정리해 미국장을 전망하는 보고서를 하루 2번.
누적된 경제 시그널을 쓰고, 이슈가 생기면 하이닉스에 미칠 영향을 말해주고,
위키에 쌓인 관심사항을 추적·검증하는 **경제 공부 파트너** 같은 보고서."

## 0. 진단 — 두 실패는 같은 원인이었다

이전 시도가 두 번 실패했다:

1. **전부 넣기** → context 폭발 → 내용이 부실해짐 → 사용자가 Routine 정지
2. **아주 간단히** → 원하는 보고서가 아님

둘 다 **선별 계층이 없어서** "전부 아니면 아무것도" 두 극단밖에 없었던 것이다.
실측이 이를 뒷받침한다:

| 대상 | 실측 | 토큰(≈1.5자/토큰) |
|---|---:|---:|
| 위키 전체 | 268페이지 6.8MB | 통째로는 불가능 |
| **리포트 1개** | 40,415자 | **~27,000** ← 주범 |
| 브리핑 팩 | 3,290자 | **~2,200** |

## 1. 원칙 — 리포트는 위키를 읽지 않는다

LLM의 `wiki/` 직접 접근을 **금지**하고, 코드가 만든 **크기 고정 팩**만 읽힌다.

| 블록 | 출처 | 만드는 주체 |
|---|---|---|
| ① 오늘의 실측 | macro-series (10지표, 1일·5일 변화) | 코드 |
| ② 하이닉스 실측 | KIS (종가·수급·ADR·신용) | 코드 |
| ③ 위키 추적 신호 | wiki_digest **선별 5개** | 코드가 선별 |
| ④ 직전 브리핑 **결론만** | report/briefing/ | 코드 |
| ⑤ 예측 원장 | predictions/ledger.csv | 코드 |

**위키가 500페이지가 돼도 팩 크기는 안 변한다** — 요약이 아니라 **선별**이기
때문이다. 오늘 안 고른 페이지는 잃는 게 아니라 다음에 고르면 된다.

미수집은 "없음"으로, 지연은 "⚠️N일 지연"으로 **명시**한다. 조용히 빼면
LLM이 있는 줄 알고 지어낸다(R3).

## 2. 선별 규칙

1. **오늘 켜진 트리거**에 대응하는 digest 우선 — FX 경고, 하이닉스 ±3%,
   미 10년물 20일 ±25bp, VIX 5일 ±20%
2. 남는 자리는 **가장 오래 안 읽힌 순**(로테이션)

2번이 없으면 조용한 축은 영원히 안 읽히고 조용히 썩는다 — 실제로 이 저장소
monitoring 15개 중 절반이 3주 이상 미갱신이었다.

## 3. 예측 원장 — "공부 파트너"의 정체

매일 잘 쓴 요약을 받아도 맞았는지 안 따지면 **매일 새로 시작하는 감상문**이다.

[FRS](fx-regime-score-design.md)에서 배운 걸 그대로 적용한다 — 전환 경고
감지기 4종을 만들고 **리프트를 측정**했더니 하나(모멘텀 반전)는 기저율보다도
나빴다. 측정하지 않았으면 넷을 같은 무게로 읽었을 것이다.

매 브리핑이 **반증 가능한 예측**을 남기고 다음 브리핑이 **데이터로 채점**한다:

```csv
id,issued_at,slot,claim,check_date,check_key,check_op,check_value,status,result
P0001,2026-09-11,AM,"미 10년물이 4.5% 이상 유지",2026-09-25,us_10y,>=,4.5,OPEN,
```

- **자유문 예측은 받지 않는다**(연산자 검증) — 그 제약이 예측을 날카롭게 만든다
- 데이터를 못 찾으면 MISS가 아니라 **UNVERIFIABLE** — 없는 걸 "틀렸다"로
  기록하면 적중률 통계가 오염된다(R3)
- 채점 가능한 키: macro-series 16종 + KIS 4종

## 4. 두 슬롯이 서로를 채점한다

| | **AM 07:30 KST** | **PM 19:40 KST** |
|---|---|---|
| 신선한 것 | 밤사이 미국, 어제 한국 종가 | **오늘 한국 종가·수급** |
| 출력 | 오늘 한국장 전망 | 오늘 밤 미국장 전망 |
| 채점 | 어제 PM의 미국장 전망 | 오늘 AM의 한국장 전망 |

**시각은 수집 스케줄에서 역산했다**(추정 아님):
- AM 07:30 ← KIS 07:00, macro-data-sync 07:10 뒤
- PM 19:40 ← KIS 3차 19:00, portfolio 19:10, exports 19:30 뒤

> 처음엔 PM을 18:30으로 제안했다가 검토에서 잡았다 — 그러면 **KRX 종가가
> 팩에 안 들어간다.**

## 5. 조용한 날 게이트 — 토큰 규율

사용자가 Routine을 정지시킨 이유가 "대충 만드는데 토큰이 아깝다"였다.
**LLM을 부르기 전에 코드가 발행 여부를 정한다**:

> 움직인 것 없음 **AND** 검증일 도래 예측 없음 → 종료코드 10 = 조용한 날
> → Routine은 아무 알림 없이 종료

매일 억지로 쓰면 내용이 묽어지고 비용만 든다.

## 6. 하이닉스 의견은 9체크포인트에 매핑

자유서술 의견은 표류한다. 오늘 사건이
[9체크포인트](../concepts/sk-hynix-analyst-thesis-checkpoints.md) 중 어디에
해당하는지 매핑하게 해서 추적 가능성과 위키 동기화를 확보한다.

## 7. 구축 중 잡은 문제들

- **분리뇌**: 데이터는 `main`에, 분석 코드는 작업 브랜치에 쌓여 있었다.
  검토 중 낡은 브랜치 사본을 보고 "수집이 멈췄다"고 오판할 뻔했다.
  2026-09-11 병합으로 해소.
- **리포트가 하루 낡은 데이터로 만들어지고 있었다**: `daily-peos-report`가
  06:00인데 `macro-data-sync`가 07:10이었다 → 07:30으로 이동.
- **백테스트 무결성 구멍**: 시계열은 `series.py`가 as_of로 자르는데
  `manual_inputs/*.yaml`만 그 필터를 안 거쳐, 1990년을 계산해도 오늘의
  지정학 판단이 켜졌다. 양쪽(점수·감지기) 모두 차단.

## 8. 발송 경로 — 왜 Routine이 아니라 Actions가 보내는가

처음엔 `scripts/publish_briefing.py`가 Routine 프롬프트 안에서 메일까지
보내게 했다. **틀렸다 — 시크릿이 있는 곳이 다르다.**

| | 시크릿 접근 |
|---|---|
| GitHub Actions | ✅ `${{ secrets.GMAIL_ADDRESS }}` |
| Routine 세션(Claude 컨테이너) | ❌ `environment_variables: {}` |

그대로 뒀으면 첫 저녁 루틴이 브리핑을 다 쓰고 마지막에 "채널 미설정"으로
종료코드 1을 내며 실패했을 것이다. **브리핑을 썼는데 아무도 못 받는 건
안 쓴 것보다 나쁘다** — 썼다고 착각하게 되기 때문이다.

**현재 구조**:

```
Routine  →  마크다운 작성 → publish_briefing.py --no-email (HTML 생성)
                                      → git push origin main
                                              ↓ (경로 감지)
GitHub Actions (briefing-email.yml)  →  HTML 변환 + 메일 발송 + 커밋
```

`push`가 곧 발송 트리거다. **push에 실패하면 메일도 안 나간다** — 루틴
프롬프트가 그 경우 사용자에게 반드시 알리도록 못박았다.

수동 발송도 된다: `workflow_dispatch`로 slot/date를 주거나, 비우면 가장
최근 브리핑을 보낸다. 2026-09-11 첫 아침 브리핑을 이 경로로 실제 발송해
`발송 완료: [PEOS 아침 브리핑] 2026-09-11` 로그까지 확인했다.

발송 실패 시엔 기존 `send_report_email --failure-alert` 경로로 알린다 —
조용한 실패를 막는 게 이 저장소의 일관된 방침이다.

## 9. 첫 실전 실패 — Routine 세션에는 저장소가 붙지 않는다 (2026-09-12)

시스템을 만든 다음 날, **자동 발행이 두 번 연속 실패했다.** 둘 다
`SUCCEEDED`로 보고됐기 때문에 실패인 줄도 몰랐다. 이 절은 그 진단 기록이다.

### 증상과 오답

`report/briefing/`에 손으로 만든 09-11 AM 하나뿐인데, Routine은 두 번 다
정상 종료(각 6분)였다.

| 가설 | 검증 | 결과 |
|---|---|---|
| 조용한 날(종료코드 10) | 게이트 재실행 | ❌ `발행`(exit 0) — 기각 |
| 보고서를 안 썼다 | 세션 `output_tokens` | ❌ 21,706 / 22,024 — **다 썼다** |
| 저장·발송 경로 고장 | 수동 push로 재현 | ❌ Actions success, 메일 발송됨 |

### 진짜 원인 ① — `sources`·`outcomes`가 비어 있었다

`session_context`를 비교하니 답이 나왔다.

| | 작업 세션 | Routine 세션 |
|---|---|---|
| `sources` | `[Repo_name, open-trading-api]` | **`[]`** |
| `outcomes` | `{repo, branches:[main]}` | **`[]`** |
| 종료 상태 | WORKING | **REVIEW_READY** |

**`create_trigger`로 만든 Routine은 호출 세션의 저장소 연결을 상속하지
않는다**(`created_via: meta_mcp`). 프롬프트에 넣어둔
`cd ... || git clone ...` 폴백이 오히려 독이 됐다 — 읽기 전용 사본이 생겨
"저장소는 있는데 push만 안 되는" 상태가 만들어졌고, 실패가 조용해졌다.
세션은 `REVIEW_READY`로 끝나고 컨테이너 회수와 함께 산출물이 사라졌다.

push가 없으니 `briefing-email.yml`도 안 돌았다(실행 이력 0건).
**§8이 설계한 실패 알림조차 발동하지 않은 이유가 이것이다** — 그 알림은
워크플로가 *돌았는데* 실패했을 때만 울린다. 워크플로 자체가 안 뜨는 경우는
§8의 사각지대였다.

### 진짜 원인 ② — UTC cron이 KST에서 요일을 하루 민다

| Routine | 기존 (UTC) | 실제 (KST) | 교정 |
|---|---|---|---|
| 아침 07:30 | `30 22 * * 1-5` | **화~토** — 월요일 없음, 토요일 헛발 | `30 22 * * 0-4` |
| 저녁 19:40 | `40 10 * * 1-5` | 월~금 ✅ | 변경 없음 |

UTC 22:30은 KST로 **다음 날** 07:30이라 요일이 밀린다. 10:40은 같은 날이라
안 밀린다. 첫 실전 실행이 두 결함을 동시에 밟았다 — **토요일 07:36에 떨어져
휴장일 "오늘 한국장 전망"을 쓰고 있었다.**

### 수정 — 상시 워커 바인딩

저장소 연결을 만들어주는 경로는 `create_session(source_url, outcome_branch)`
뿐이다. 그래서 워커 세션 2개를 만들고 Routine을 `persistent_session_id`로
바인딩했다(`update_trigger`로는 저장소 연결을 바꿀 수 없어 삭제·재생성).

```
Routine (cron)  →  워커 세션 (sources + outcomes:main)  →  git push
                                                              ↓
                                            briefing-email.yml  →  메일
```

트레이드오프: 워커가 상시 세션이라 **실행 맥락이 누적된다.** 그래서 프롬프트
0단계에 "매 실행은 독립이다 — 이전 대화의 기억을 쓰지 마라"를 박았다. 팩이
매번 새로 생성되므로 숫자의 출처는 여전히 코드 하나다.

### 프롬프트에 추가된 3가지 (전부 실측으로 얻음)

1. **`git checkout main` 필수** — 워커는 detached HEAD로 시작한다.
   그 상태로 커밋하면 push가 아무 데도 안 간다.
2. **`pip install -r requirements.txt` 필수** — 컨테이너가 재활용되면
   pandas가 사라져 테스트가 수집 단계에서 27건 통째로 실패한다.
3. **push 성공을 눈으로 확인하라** — `main -> main` 출력과 `ahead 0`를
   확인하고, 4회 실패 시 마크다운 전문을 채팅에 남겨 유실을 막는다.

### 남은 문제 — 거래일 달력이 없다

자동 수집이 UTC 기준이라 **주말에도 날짜를 찍는다.**
`signal_2026-09.csv`가 9/10 다음 9/11(금)을 건너뛰고 9/12(토)를 기록했고,
예측 `P0001`도 검증일이 토요일인데 금요일 종가로 채점됐다. 결론(적중)은
바뀌지 않지만 근거가 흐려진다. 프롬프트에 "검증일은 거래일로 잡아라"를
넣어 완화했을 뿐, **근본 해결은 거래일 달력 도입이다** — 미해결.

### 교훈

**"SUCCEEDED"는 산출물이 남았다는 뜻이 아니다.** 이 시스템은 발행 성공을
Routine의 종료 상태로 판단하고 있었는데, 그 둘은 무관했다. 산출물의 존재를
직접 확인하는 경로가 없으면 실패가 조용히 지나간다.

## 10. CPI 프레임 오류 + 캘린더 인지 + 주간 전망 (2026-09-12)

### 10.1 컨센서스 서프라이즈를 추세 전환으로 오독

09-12 아침 브리핑에서 "8월 근원 CPI가 예상(+0.2%)을 웃돈 +0.3%"만 보고
"인하 지연이 인상으로 바뀌었다"고 썼다. 사용자가 "CPI가 6월 정점 찍고
추세 하락 중 아니냐"고 지적 — 확인해보니 맞았다: YoY는 6월 2.6%→7월
2.5%→8월 2.4%로 **계속 하락**했다. 8월치가 컨센서스보다 높았던 건
사실이지만, 그건 **한 달 서프라이즈**일 뿐 **레벨 추세**는 그대로였다.
서프라이즈와 추세를 혼동하면 "물가가 다시 뛴다"는 반대 결론이 나온다.

수정은 코드가 아니라 **판단 습관**이다 — 발표치를 인용할 때 직전 몇 달
추세를 함께 확인하고, 추세 전환을 주장하려면 최소 2~3개월 연속 확인을
요구하도록 AM/PM 프롬프트 2단계에 이 사례를 실측 경고로 박았다. 이미
나간 09-12 브리핑은 조용히 고치지 않고 **정정 섹션을 파일 상단에
추가**해 오류를 남겼다(추적성 — CLAUDE.md Traceability 원칙).

### 10.2 거래 캘린더 인지 (`engine/briefing/calendar.py`)

사용자 요청: "한국과 미국에 거래 없는 날을 알고, 그게 두 시장 사이
time delay로 어떻게 작용할지 의견에 포함돼야 한다."

기존 팩은 데이터의 **기준일**(⚠️N일 지연)만 알 뿐, 그 지연이 **휴장
때문인지 단순 수집 지연인지**를 구분 못 했다. 새 모듈이 그 구분을
코드로 만든다:

- `data/manual_inputs/market_holidays_2026.yaml` — KR/US 확정 휴장일
  (KRX·NYSE 공지 종합, 매년 수동 갱신 필요)
- `is_trading_day()` / `last_trading_day()` — 요일+휴장일로 거래일 판정
- `describe_trading_gap(as_of, slot)` — AM은 "미국이 며칠 쉬었다 재개됐는가"

## 11. HTML이 md와 구분이 안 됐다 + 결론이 너무 늦게 나온다 (2026-09-16)

사용자 피드백 두 가지, 같은 날:

1. "경제 전문가의 날카로운 분석이나 전망이 전혀 없다."
2. "양식이 줄도 안 맞고 숫자도 안 맞고 타이틀과 내용의 구분도 잘 안된다.
   md file과 html보고서가 차이가 없다. 너무 성의가 없는데?"

실측으로 원인 두 개를 각각 확인했다.

### 11.1 `render_html.py`의 번호 목록 파서가 계속줄을 놓치고 있었다

`engine/briefing/context.py`가 만드는 팩도, Routine이 쓰는 실제 브리핑도
번호 목록 한 항목이 **들여쓴 계속줄**로 여러 줄에 걸친다(마크다운 소프트
줄바꿈 — 표준 관행). 예:

```
1. **지수는 소폭 하락, 그런데 금리가 19년 최고를 찍었다.** S&P500 -0.16%,
   나스닥 -0.26%, 다우 -0.49%로 지수 낙폭은 작았다. ...
```

옛 `markdown_to_body()`는 `^\d+\.\s`로 시작하는 줄만 목록 항목으로 인식했다
— 들여쓴 계속줄은 이 패턴에 안 걸려 목록 루프가 끝나버리고, 나머지 문장이
**별도 `<p>`로 떨어져 나갔다.** 결과: 문서 전체의 모든 번호 목록이 "1."로
시작하는 첫 줄만 목록이고 나머지는 목록 밖 평문으로 갈라져 있었다 —
사용자가 본 "줄이 안 맞는다"는 지적의 정체가 이것이었다. 별도 실험 없이
`report/briefing/2026-09-16-AM.html`을 직접 열어 확인했다(`<ol><li>...,</li>
</ol><p>나스닥 ...</p>` 패턴이 6개 섹션 전부에서 반복).

수정: 목록 파서가 들여쓴 비-헤딩/비-테이블 줄을 **현재 항목에 이어붙이게**
재작성(`engine/briefing/render_html.py`). 비순서 목록도 동일 로직 공유.

### 11.2 `_CSS`의 카드·배지 클래스를 렌더러가 한 번도 안 썼다

`engine/report/html_shared.py`의 `_CSS`엔 `.card`·`.badge-*`·`.action-card`
등 시각적 위계를 만드는 클래스가 이미 있었다(월간 리포트·대시보드용). 그런데
`render_html.py::markdown_to_body()`는 `<h2>`/`<p>`/`<table>`/`<blockquote>`를
**아무 컨테이너 없이 평평하게** 이어붙일 뿐, 이 클래스들을 전혀 참조하지
않았다. 그래서 HTML을 열어도 raw markdown을 읽는 것과 체감이 같았다 —
"md와 html이 차이 없다"는 지적이 정확했다.

수정 (모두 `render_html.py`, 코드만 — LLM 출력 형식은 그대로):

- `##` 섹션마다 `<section class='card'>`로 감싼다(`_wrap_sections`). `##
  결론` 섹션만 `card highlight`(강조 테두리).
- 🔴🟠🟡🔵✅❌⚠️로 시작하는 인용문·소제목(`###`)에 그 등급 색의
  배경/테두리를 입힌다(`_leading_severity` → `bq-*`/`hx-*` 클래스). 번호가
  앞에 붙는 위키 신호 제목("1. 🟢 원화...")도 번호를 건너뛰고 이모지를 찾는다.

### 11.3 "결론"이 문서 8개 섹션 뒤, 그것도 헤지된 관찰 나열이었다

렌더링과 별개로, **콘텐츠 자체**도 확인이 필요했다. `2026-09-16-AM.md`를
전문 검토한 결과: 자료·인용·자기검산(당일 산식 오류 자체 포착, 채점
설계 결함 자기비판 등)은 이미 상당히 충실했다. 문제는 **확신에 찬 판단이
문서 맨 끝 `## 결론`에만, 그것도 "판단을 바꾸지 않는다/단정하지 않는다"류
헤지로 나온다**는 것 — 8개 섹션을 다 읽어야 "그래서 오늘 어떻게 하라는
거냐"가 나왔다.

Routine 프롬프트는 상시 워커 세션에 바인딩돼 있어 `update_trigger`로 직접
수정이 안 된다(§9에서 이미 확인된 플랫폼 제약 — "persistent_session_id에
바인딩된 Routine의 프롬프트는 이 도구로 못 바꾼다"). §10.2의 거래 캘린더
필수 검색 체크리스트와 같은 방식으로 우회한다 — **팩 콘텐츠에 지침을
박는다.** `build_style_directive_block()`(`engine/briefing/context.py`)이
새 톤 지침 블록을 pack 두 번째 자리(데이터 헬스 다음)에 추가했다:
H1 바로 다음에 확신 어조의 `## 오늘의 판단` 절을 새로 쓰게 하고, "엇갈린다/
지켜봐야 한다/단정하기 이르다"로 문장을 끝내는 것을 금지어로 명시했다.
다음 발행(2026-09-16 PM)부터 반영 여부를 실측 확인해야 한다 — **미검증**.

## 12. 지연 지표의 "뉴스 교차검증"을 특정 3개에서 전체로 일반화 (2026-09-18)

### 12.2 "다른 API로 같은 정보"는 성립하지 않는다

사용자가 "다른 API가 동일 정보를 주는지 알아보라"고 요청했으나, 실시간으로

다르다. 대체가 아니라 **별도 지표 병기**로 가야 한다는 걸 먼저 밝히고,
1단계(즉시)·2단계(신규 DXY 수집기, 사용자 확인 대기 중)·3단계(실질
영향 재점검)로 계획을 나눴다.

### 12.3 일반화 — 3개 지표에만 붙어 있던 처리를 전체로

사용자가 이어서 "몇일씩 delay되거나 오늘자 데이터가 아닌 것들 **전부**에
대해 웹검색 Plan B를 뚫으라"고 요청. 점검해보니 AM 브리핑에 이미 있던
"뉴스로 보정되는 칸"(지연된 FRED 값 옆에 뉴스 실측치를 병기하는 표)이
**미 10년물·브렌트유·원/달러 3개에만** 적용되고 있었다 — 이유는
2026-09-14 사고 당시 그 3개가 마침 걸렸던 지표였기 때문이지, 체계적
규칙이 있었던 게 아니었다. **오늘은 달러지수가 걸렸는데 목록에 없어서
빠졌다** — 하드코딩의 실체가 이거였다.

**수정**(`engine/briefing/context.py::build_fact_sheet`): `⚠️N일 지연`
마크를 붙이는 것과 **같은 기준(age≥3일)** 으로 지연 지표를 전부
수집해서, 팩에 "🔎 뉴스 교차검증 필수 목록"을 **그날 실제로 지연된
지표만** 동적으로 나열하도록 일반화했다. 특정 지표 이름을 하드코딩하지
않는다 — 내일 다른 지표가 걸리면 그 지표가 자동으로 목록에 오른다.
지연이 하나도 없는 날은 체크리스트 자체가 안 붙는다(경고 남발 방지 —
이 저장소가 데이터 헬스 제어 루프에서 이미 배운 원칙과 동일).

**적용 범위의 한계, 명시**: 이 메커니즘(LLM이 웹검색으로 보정)은
**브리핑(AM/PM/WEEKEND)에만 적용된다.** 월간 PEOS 리포트(`engine/
report/run.py`)는 `python -m engine.report.run`으로 실행되는 **순수
코드 파이프라인**이라 LLM이 개입하지 않는다 — 웹검색을 할 주체 자체가
없다. PEOS 리포트 쪽 지연은 이미 있는 Section -1 데이터 헬스 배너로

### 12.4 2단계 — ICE DXY 병기 (같은 날 실행)

이 저장소가 반복해서 겪은 "다른 정의를 같은 값으로 쓴 사고"(체결/결제,
WTI/Brent, 잠정치/확정치)와 정확히 같은 계열의 실수가 된다.

**이 소스가 언젠가 막히면**: 무인증 공개 엔드포인트라 예고 없이 차단될
수 있다. 그때는 이 계열만 갱신이 멈추고 §12.3에서 일반화한 "뉴스
교차검증 필수 목록"이 자동으로 집어낸다 — 조용히 사라지지 않는다.
두 작업이 서로를 받쳐주는 구조다.

팩 크기는 7,203자(상한 24,000·회귀선 12,000 모두 여유).

DXY 쪽은 `tests/test_macro_data_yahoo.py` 7건 신설 — 타임스탬프→UTC
거래일 변환, `close=null`(휴장일) 건너뛰기, **봇 차단 본문이 왔을 때
조용히 넘어가지 않고 죽는지**(stooq가 정확히 그렇게 실패했다),
프리셋이 FRED 계열을 덮어쓰지 않고 별도로 등록됐는지, 팩트시트 라벨에
"참고"가 있는지. 전체 회귀 **589건 통과**.

**운영 검증(코드 리뷰가 아니라 실제 실행)**: `macro-data-sync.yml`을
workflow_dispatch로 돌려(run 35339084289) 실제 수집 확인 —
`us_dollar_index_dxy`가 2026-09-11~09-18까지 6행 upsert됐고 커밋
`52ba4a8`로 푸시됐다. 그 데이터로 팩을 렌더링한 결과:

```
| 달러지수            | 118.21 | ... | 2026-09-11 ⚠️7일 지연 |
| 달러지수(DXY·참고)  | 100.42 | ... | 2026-09-18            |
```

**지연 경고는 그대로 유지하면서(숨기지 않는다) 당일 달러 방향은 볼 수
있는** 상태가 됐다. 두 값이 118.21 vs 100.42로 나란히 찍히는 것 자체가
"이 둘은 다른 지수"라는 걸 읽는 사람에게 계속 상기시킨다.
