CXL Memory Expansion — Chart Impact Analysis

📅 2026-08-21  |  🔬 Local CXL (PCIe 5.0) + Out-Rack CXL Pooled → 12 포인트全部 계산
"NVLink-C2C를 통한 SOCAMM2 spill-over"만 있던 아키텍처에 "CXL memory tier"를 추가하면 chart가 어떻게 변하는가?

📋 Tier별 Bandwidth Hierarchy (Revisited)

기존 Tier hierarchy: HBM4 → SOCAMM2 → CXL (KV cache 부적합) → SSD
新问题: CXL이 정말 "KV cache 부적합"인가? CXL 2.0/3.0 memory expander의 spec을 보면...

CXL Local (PCIe 5.0 x8) — Server-Local Expansion

Spec:
  Physical: PCIe 5.0 x8 (Samsung CXL Expander, Advantech CXL 2.0 module)
  Raw bandwidth: 32 GT/s/lane × 8 lanes = 256 GT/s
  Effective (PCIe 5.0 encoding): ~64 GB/s raw → ~45-50 GB/s usable
  Latency: ~5-10 μsec (PCIe hop + CXL controller)

Per-Module:
  Capacity: 256 GB per CXL DIMM (DDR5-based)
  Bandwidth: 45-50 GB/s (single x8 PCIe 5.0)

Per-Server (NVL72, 72 GPU, 36 CPU cores):
  PCIe slots per CPU: 8-16 x8 lanes
  CXL modules per server: 1-8 modules
  ───────────────────────────────────────
  Bandwidth: 45-400 GB/s (1-8 modules)
  Capacity: 256-2,048 GB (1-8 modules)

Out-Rack CXL Pooled — Rack-External Pooling

Spec:
  Network: 100GbE or 200GbE (RDMA/RoCE)
  Protocol: CXL over Fabric (CXL.FT)
  Effective bandwidth (RDMA): 9-18 GB/s per 100GbE
  Latency: ~50-200 μsec (network hop + CXL)

Per-Server:
  100GbE NIC × 4 = 36 GB/s effective
  200GbE NIC × 2 = 36 GB/s effective
  ───────────────────────────────────────
  Bandwidth: 9-72 GB/s (depends on NIC config)
  Capacity: Shared pool (10-100 TB across rack)
  Note: RDMA overhead for KV random access makes effective BW much lower

💡 핵심: CXL Local vs SOCAMM2 — CXL이 더 빠를까?

SOCAMM2 (per CPU): 1.2 TB/s → 40 CPUs → 48 TB/s total
  → NVLink-C2C: ~1.0 μsec latency
  → GPU↔CPU chip-to-chip, low latency

CXL Local (8×PCIe5): ~5 TB/s
  → PCIe 5.0 hop: ~5-10 μsec latency
  → PCIe switch + CXL controller overhead

Conclusion:
  SOCAMM2는 BANDWIDTH가 더 빠름 (48 TB/s vs 5 TB/s)
  CXL Local은 LATENCY가 더 느림 (5-10 μsec vs 1 μsec)

  하지만 CXL Local은...
  1. SOCAMM2보다 더 많은 CAPACITY를 추가 가능 (256GB-2TB per module)
  2. SOCAMM2는 CPU에 고정되어 있어 GPU당 접근이 제한적
  3. CXL Local은 PCIe slot에 직접 붙여 GPU에 더 근접 가능

  → CXL Local의 value = "SOCAMM2보다 훨씬 많은 capacity 추가"
    (SOCAMM2는 80TB/rack, CXL은 2-4TB per server 추가 가능)
  → CXL Local의 weakness = SOCAMM2보다 BW가 낮고 latency도 높음

📐 Weighted Sum Model — CXL Tier 추가

기존 formula에 CXL Local tier를 추가:

Token/Sec = IF(KV < HBM_Thresh,
                HBM_BW / KV_Cache,
              IF(KV < (SOCAM_Thresh + CXL_Local_Thresh),
                1 / (
                  (HBM_Thresh/KV)/HBM_BW +
                  ((SOCAM_Thresh+KV_local)/KV)/SOCAM_BW +
                  (CXL_Local_Thresh/KV)/CXL_BW,
                IF(KV < CXL_Pooled_Thresh,
                  ... (CXL pooled) ...
                ELSE
                  ... (SSD) ...
                )
              )
            )
          )
```

Key change: CXL Local이 SOCAMM2와 SSD 사이에 등장. SOCAMM2를 일부 대체 가능.

## H100 Impact (Memory-Bound @ x=50)



  
📍 H100 @ x=50: Original 0.15M → CXL Local 추가

  
Original:
  KV Cache = 2.7 TB (all HBM, fitting)
  HBM BW = 241 TB/s
  KV BW used = 2.7TB × 9,750 TPS / 241TB = 91% → memory-bound

  TPS = 241 TB/s / (2.7 TB × 88 layers)
      = 241,000 / 237.6 = 1,014 TPS? No...

  Correct: TPS = HBM_BW / KV_access_per_iteration
  KV_access_per_iter = batch × 0.453 MB × 88 layers
  HBM BW = 241,000 MB/s

  batch = 175 decode users
  KV_access = 175 × 0.453 × 88 = 6,978 MB = 6.98 GB/iteration

  TPS = 241,000 MB/s / 6.98 GB = 241,000 / 6,978 = 34.5 TPS...

  Hmm, the numbers don't match 9,750 TPS directly. Let me use the
  production data directly.

  Production: 91% HBM BW → 9,750 TPS @ batch 195 users.
  This means: at HBM saturation, throughput = 9,750 TPS.

  CXL Local impact: H100 @ x=50 is ALREADY HBM-saturated (91%).
  Adding CXL would only help if KV cache doesn't fit in HBM.
  But 2.7 TB fits in H100 NVL72 (5.17 TB available).

  → CXL Local 추가 시: NO IMPROVEMENT expected.
  → H100 @ x=50은 HBM이 충분하므로 spill-over 없음.
  → CXL이 chart에 미치는 영향: 0% (변화 없음)
  

  
Verdict: CXL Local: 0% improvement. HBM에 KV fitting → spill-over 없음.

## B300 Impact (Memory-Bound → Transition)



  
📍 B300 @ x=50: Original 0.75M → CXL Local 추가 시

  
Original:
  Concurrent users = 1,815
  KV Cache = 1,815 × 14.1 GB = 25.6 TB
  HBM Capacity = 288 GB × 72 = 20.2 TB
  → Spill-over to SOCAMM2: 25.6 - 20.2 = 5.4 TB

  Weighted BW (SOCAMM2 only):
  = 1 / ((20.2/25.6)/576 + (5.4/25.6)/44)
  = 1 / (0.001386 + 0.004796)
  = 1 / 0.006182
  = 161.8 TB/s effective

  TPS = 161,800 MB/s / (25,600 MB × 88 / 1,000)
  ... let me use the simpler formula:

  Weighted BW = 161.8 TB/s (effective for KV cache)
  TPS = BW / (KV_access_per_token × 88 layers)
  = 161,800,000 MB/s / (0.453 MB × 88)
  = 161,800,000 / 39.86 = 4,060,000? Too high.

  OK, the weighted BW formula gives the effective bandwidth for the
  entire KV cache. But for decode, we need per-token read throughput.

  Let me use the production-calibrated model:
  H100: 91% HBM → 9,750 TPS
  B300: 70% HBM → 0.75M TPS/MW = 90,750 TPS (chart)

  At x=50, B300 spill-over = 5.4 TB to SOCAMM2.
  SOCAMM2 BW = 44 TB/s (for spill-over portion).

  With CXL Local expansion (8×PCIe5, 400 GB/s total):
  → First 400 GB of spill-over goes to CXL (faster than SOCAMM2 for random)
  → Remaining spill-over: 5.4 TB - 0.4 TB = 5.0 TB to SOCAMM2

  Actually, CXL is SLOWER for random KV access than SOCAMM2:
  - SOCAMM2: 1 μsec latency, 1.2 TB/s per CPU
  - CXL Local: 5-10 μsec latency, 50 GB/s per module

  So CXL Local is NOT a good KV cache destination!
  SOCAMM2 (NVLink-C2C) is FASTER for KV cache access.

  CXL Local's value proposition for KV cache:
  → It provides EXTRA capacity when SOCAMM2 is also full
  → But CXL is slower than SOCAMM2 for random access

  So CXL doesn't "replace" SOCAMM2; it "extends beyond SOCAMM2".

  B300 x=50:
  SOCAMM2 capacity: 2 TB/CPU × 40 CPUs = 80 TB
  KV spill-over: 5.4 TB
  SOCAMM2 has PLENTY of room for 5.4 TB spill-over.

  → CXL Local: NO improvement needed. SOCAMM2 is sufficient.
  → CXL Impact: 0%
  

  
Verdict: CXL Local: 0% improvement. SOCAMM2 (80TB) handles spill-over easily.

## R100 Impact (Compute-Bound → Transition) — CXL이 의미 있는 경우



  
📍 R100 @ x=50: Original 1.60M → CXL Local + Out-Rack 추가

  
KV Cache = 6,368 users × 14.1 GB = 89.8 TB
HBM4 Capacity = 20.2 TB
SOCAMM2 Capacity = 80 TB

Spill-over breakdown:
  HBM4: 20.2 TB (first tier)
  SOCAMM2: min(80 TB, 89.8 - 20.2) = 69.6 TB
  Beyond SOCAMM2: 89.8 - 20.2 - 80 = -10.4 TB → NEGATIVE (all fits!)

  Wait — 20.2 + 80 = 100.2 TB > 89.8 TB total.
  → ALL KV cache fits in HBM4 + SOCAMM2!
  → No CXL needed?

  But earlier analysis showed spill-over to SOCAMM2 IS happening.
  The issue is not capacity — it's that HBM4 can't hold 89.8 TB alone.
  So 69.6 TB is in SOCAMM2, not SSD.

  With CXL Local (8 modules × 256 GB = 2 TB):
  → CXL is SLOWER than SOCAMM2 for random KV access (5-10 μsec vs 1 μsec)
  → CXL Local would replace SOCAMM2 for the first 2 TB of spill-over?

  Actually, that's the WRONG question. The right question is:
  "Does adding CXL Local tier reduce the SOCAMM2 spill-over volume?"

  No — CXL Local provides additional capacity, not replacement.

  Current: 20.2 TB HBM + 69.6 TB SOCAMM2 = 89.8 TB total
  With CXL Local (2 TB): 20.2 + 67.6 SOCAMM2 + 2.0 CXL = 89.8 TB

  Weighted BW with CXL:
  = 1 / ((20.2/89.8)/1584 + (67.6/89.8)/44 + (2.0/89.8)/5)
  = 1 / (0.000142 + 0.0169 + 0.00445)
  = 1 / 0.0215 = 46.5 TB/s

  Without CXL (all SOCAMM2):
  = 1 / ((20.2/89.8)/1584 + (69.6/89.8)/44)
  = 1 / (0.000142 + 0.0176)
  = 1 / 0.0177 = 56.5 TB/s

  Wait — CXL makes it WORSE? Because CXL is SLOWER (5 TB/s) than SOCAMM2 (44 TB/s).

  This confirms: CXL Local is a TERRIBLE KV cache destination.
  It should NOT be used for KV cache at all!

  → CXL Local impact: -18% (WORSE than SOCAMM2)
  → CXL should NOT replace SOCAMM2 for KV cache.
  → CXL's value = capacity expansion, not KV cache acceleration.
  

  
Verdict: CXL Local: WORSE than SOCAMM2. Do NOT use for KV cache.

## Out-Rack CXL Pooled — 언제 의미가 있는가?



  
📍 Out-Rack CXL Pooled Impact — Large Context Scenario

  
Out-Rack CXL Pooled: 100-200GbE RDMA, ~0.5-1 TB/s effective for KV random
Latency: 50-200 μsec (network hop)

Out-Rack CXL이 의미 있는 scenario:
1.超长 context (128K, 400K) — KV cache가 SOCAMM2도 넘어감
2.超大 batch — thousands of concurrent users
3. Multi-tenant — GPU가 여러 모델의 KV cache를 공유

For the 235B model at current chart points:
  All KV caches fit in HBM4 + SOCAMM2 (combined 100 TB)
  → Out-Rack CXL: 0% improvement at ANY point

Out-Rack CXL impact ONLY appears when:
  KV Cache > 100 TB (HBM4 20.2 + SOCAMM2 80)
  → Requires >7,000 concurrent users × 14.1 GB
  → Or longer context (128K → 4x × 7,000 = 28,000 users needed)


  
Verdict: Current chart points: 0%. Only matters for 128K-400K context + large batch.






  
💡 Out-Rack CXL이 chart를 바꾸는 경우

  

    128K context (Medium tier, Kimi K2.5):

    KV per user = 0.453 MB × 4 × 88 = 159.4 MB (32K의 4배)

    KV per user = 159.4 MB → 128K context로 11.3 GB/user


    B300 @ x=50, Medium tier: ~1,815 users

    KV total = 1,815 × 11.3 GB = 20.5 TB

    HBM4 = 20.2 TB → spill-over = 0.3 TB

    SOCAMM2 handles 0.3 TB easily.

    → Out-Rack CXL: 0% impact.

    But if batch increases to 5,000 users:
    KV total = 5,000 × 11.3 = 56.5 TB

    HBM4 = 20.2 TB → spill-over = 36.3 TB

    SOCAMM2 = 80 TB → still handles 36.3 TB.

    → Out-Rack CXL: still 0% impact.

    SOCAMM2 (80 TB) is surprisingly generous for most workloads.
  

  

    400K context (Premium tier, GPT MoE 2T):

    KV per user = 0.453 MB × 12.5 × 88 = 498.6 MB = 0.5 GB

    At x=400, Premium tier: ~100 users (from chart)

    KV total = 100 × 0.5 = 50 GB

    → CXL: 0% impact.

    BUT: if batch grows to 5,000 users:
    KV total = 5,000 × 0.5 = 2,500 GB = 2.5 TB

    HBM4 = 20.2 TB → fits easily!

    → CXL: still 0% impact.

    Conclusion: CXL is NOT needed for KV cache in any chart point scenario.

When WOULD CXL Change the Chart?




  
Scenario 1: Extreme Batch Size (10,000+ users)

  
R100 @ 10,000 users × 14.1 GB = 141 TB KV cache

  HBM4 = 20.2 TB → SOCAMM2 = 80 TB → remaining = 40.8 TB

  → CXL Local (2 TB) + Out-Rack CXL (20 TB) needed

  → CXL spill-over BW ~1 TB/s → weighted BW drops

  → TPS/MW: 1.60M → ~0.9M (44% reduction) at x=50

  → Chart curve pushes DOWN at large batch sizes






  
Scenario 2: Ultra-Long Context (400K+)

  
GPT MoE 2T @ 400K context: KV per user ~2 GB (large MoE KV)

  5,000 users × 2 GB = 10 TB → HBM4 handles this

  10,000 users × 2 GB = 20 TB → HBM4 full, SOCAMM2 needed

  20,000 users × 2 GB = 40 TB → SOCAMM2 needs 20 TB spill-over

  → CXL becomes relevant for >15K users at 400K context

  → Chart for x=400 Premium tier: curve pushes DOWN at extreme scale
