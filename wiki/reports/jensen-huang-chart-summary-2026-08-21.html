2. 첫 역산 — H100 (50, 0.15M)의 정체

차트에서 가장 왼쪽 아래 점 — "Free 티어, Qwen 3, 235B, 32K" — 이 점이 의미하는 real-world 조건을 완전히 역산해보자.

Step-by-step 역산

차트 점: x=50 (TPS/User), y=0.15M (TPS/MW)

Power 기반 Total TPS 계산:
  H100 NVL72:  700W × 72 = 50.4kW GPU
  Rack total:  ~65kW (cooling, network ×1.29)
  → 65kW = 0.065 MW

  Total TPS = 0.15M × 0.065 = 9,750 TPS

Concurrent Users:
  9,750 TPS ÷ 50 TPS/User = 195 users

LLM — Qwen 235B Class (Dense):
  Parameters:  235B  |  Layers: ~88  |  FLOPs/token: 470B
  Context:     32K   |  GQA: 128 query → 8 KV heads

KV Cache:
  Per-token: 2 × 128 × 8 × 2 × 88 = 0.453 MB
  Per-user (32K): 0.453 × 32,000 = 14.1 GB
  Total (195 users): 2.7 TB → HBM 5.17TB 내에 fitting ✓

GPU Compute:
  H100 FP8 dense: 989 TFLOPS/GPU × 72 = 71,208 TFLOPS
  Required: 9,750 × 470B = 4,582 TFLOPS
  → GPU Utilization = 6.4%
첫 결론 (나중에 틀린 걸로 판명됨)
"195 ÷ 72 GPUs = batch 3/GPU. GPU가 batch 3개로 동작하므로 tensor core가 거의 idle. bottleneck = small batch inefficiency."

3. 문제 발견 — "batch 3"은 말이 안 된다

여기서 큰 의문이 생겼다. "batch 3/GPU가 현실적인가?"

🚨 batch 3 가설의 문제
H100 single-GPU에서 decode optimal batch는 32 (논문 검증). batch 3은 batch 32보다 bandwidth efficiency가 훨씬 낮고, "batch 32에서 throughput scaling이 깨진다"는 연구 결과가 있음. 또한 195 users가 batch 3으로 72 GPU에 "분리된다"는 개념 자체가 Tensor Parallelism을 오해한 것 — TP는 computation split이지 batch split이 아님. 모든 GPU가 같은 batch를 함께 처리.

그렇다면 batch size는?

batch size를 outcome으로 역산하되, GPU/Memory/SW overhead를 현실적으로 가정해서 다시 계산했다. 그 결과가 Section 5에 있다.

🎯 가장 중요한 발견 — Decode는 ALWAYS Memory-Bound for 235B

235B dense model의 arithmetic intensity:

  Total FLOPs = batch × 470B
  Total memory read = batch × 39.86 MB (88 layers)
  Ops/byte = 470B / 39.86 MB = 11.8 ops/byte

  threshold: 60-80 ops/byte (memory-bound 경계)
  11.8 <<< 60 → ANY batch size에서 decode는 memory-bound!

  → 235B 같은 대형 모델은 batch 3이든 3,000이든
    decode는 inherently memory-bound.
    "batch 3이 bottleneck"이라는 가설이 무너졌다.

🎯 Revised Bottleneck 정의

  1. KV Cache L2 miss (56%) — 32K context가 너무 커서 L2 cache에 안 떨어짐. L2 hit rate 0.83% → 98%+가 HBM 직접 읽기 → stall
  2. Prefill Overhead (35%) — new sequence arrival cost. decode보다 10,000X 느린 prefill이 mixed workload에서 dominant
  3. compute (6.8%) — tensor core는 거의 idle (GPU util 6.8% → research 20-40%와巧合로 일치)

🎯 Bottleneck Evolution의 핵심

H100: Decode가 HBM bandwidth의 91%를 먹는다 → memory bottleneck → 해결책 = KV quantization + prefill/decode disaggregation

B300: FP8 quant + FP4 native로 decode BW 70% → ↓ 하지만 여전히 memory-bound → 해결책 = KV quant + FP4 native + software opt

R100: HBM4 22TB/s로 decode BW 25% → compute bound로 전환! bottleneck이 software(previewl overhead)로 이동 → 해결책 = software만 개선하면 됨

7. 핵심 결론 — 3줄 요약

1. Bottleneck은 "batch 3"이 아니라 "KV Cache L2 miss"
235B 모델은 batch 3이든 3,000이든 decode는 inherently memory-bound (arithmetic intensity 11.8 ops/byte << threshold 60). 진짜 bottleneck은 32K context → PagedAttention scattered pages → L2 miss rate 98%+.
2. 세대별 개선 = HW + Software + Algorithm의 동시 진전
H100(2024): memory-bound (91% HBM) → B300(2026): 완화 (70%) → R100(2027): compute-bound (25%) HBM4 22TB/s가 memory bottleneck을 근본 해결. FP4 native가 compute density 25X.
3. R100에서는 Bottleneck이 Software로 이동
HBM4로 메모리 문제 해결되면, 남은 bottleneck은 "prefill overhead (33%)" — 이는 software optimization(previewl caching, PD disaggregation)으로 해결 가능. 2027년 이후 LLM 추론은 Hardware-driven → Software-driven으로 전환됨.
